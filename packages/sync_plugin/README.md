# Ядро синхронизации

Экспериментальный первый этап [архитектуры](../../docs/device-sync.md).
`sync_logic.dart` — чистая Dart-точка входа: версии, причинный граф, строгий
кодеки задач/WorkLogs/проектов/целей/сфер/тегов, контракты и обмен без транспорта.

DriftSyncStore находится в приложении (`lib/features/sync/data/`).
После `initialize(datasetId)` можно вызывать `saveTask`/`deleteTask`, передавая
ожидаемые ID вершин. `SyncEngine.exchange(a, b)` обменивает два SyncStore.
Это программный стенд для доверенных локальных объектов, не сетевой протокол.

Нативная точка входа — sync_native.dart: LanSyncService (`sync.local`) с TLS,
pin сертификата, отдельным ключом пары, подтверждением приглашения и отзывом.
Web выбирает заглушку. Flutter и хранилище ОС остаются адаптерами приложения;
секреты передаются через SyncSecretStore. Подключение UI — через plugin_ui.
ENABLE_SYNC по умолчанию false, listener/bootstrap включаются явно.
В приложении DAO получают TaskMutationJournal через конструкторы. До явного
bootstrap он пропускает операции; подключённая база продолжает вести журнал
после перезапуска. experimentalSyncDatasetId в DependencyContainer предназначен
для тестового включения. Полные обновления Task проверяют storageRevision,
прочитанный DAO и сохранённый copyWith.
Этап 2б поддерживает иерархию задач и отдельные ревизии WorkLogs; полное
обновление WorkLog также проверяет storageRevision. Графовые удаления задач
и keepChildren передаются атомарными группами, включая каскадные WorkLogs.
Неполные группы и недостающие связи остаются pending в журнале после перезапуска.
repairPendingTask позволяет явно исправить структурный цикл с проверкой основы.
Схема 12 добавляет переносимый UUID Tags.syncId, сохраняя локальные integer ID.
Этап 2в поддерживает всю иерархию сфера/цель/проект/задача, отдельные теги
и групповые удаления. Первичные версии и UUID тегов создаёт явная initialize
в одной транзакции; повторный initialize явно обновляет старую экспериментальную
базу без перезаписи прежних ревизий. Project/Goal/Sphere также имеют storageRevision;
редакторы графа сверяют версию открытого узла через attributes.
Одноимённые независимые теги остаются pending; repairPendingEntity позволяет
явно исправить имя/структуру с сохранением истории. saveEntity/deleteEntity
дают программное разрешение конфликтов с проверкой ожидаемых вершин.
Изменение задачи в обход журнала блокирует её перезапись и экспорт.
Все store должны использовать одну AppDatabase на локальную БД; закрывает её
владелец после завершения операций. Экземпляр store не открывает ресурсы сам.

Вершины и pending вычисляются из журнала при чтении; история не удаляется.
Это реализация для небольшого тестового набора, перед масштабированием нужны
индексы и сохранённая проекция. Ревизии v1 читаются без изменения, v2 добавляет
тип сущности и manifest группы. Размер группы пока ограничен 1000 ревизиями.
v3 добавляет новые типы и UUID тегов в задачах, v1/v2 читаются без изменений.
Ручной LAN и UI состояния/конфликтов/pending реализованы; mDNS/QR/фон,
привычки, файлы и масштабирование — далее. stop отзывает сессии и дожидается
принятых операций БД до закрытия хранилища. Настройки и инструкция подключения:
[docs/local-sync.md](../../docs/local-sync.md). Полевого прогона Windows ↔ Android
пока нет; сетевые тесты используют реальные TLS на loopback и отдельные SQLite.

Проверки: `flutter test test/features/sync test/core/database`.
Чистое ядро: `dart test test/features/sync/sync_graph_test.dart` из корня workspace.
