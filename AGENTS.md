# Life OS: контекст и правила работы

Этот файл описывает текущее состояние проекта для нового чата. Он действует на весь репозиторий. Начинай с него, затем читай только относящиеся к задаче файлы. Историю предыдущего чата считать доступной не нужно.

## Что это за приложение

Life OS — личный органайзер на Flutter/Dart с локальным хранением: задачи, проекты, цели, сферы жизни, привычки и заметки. Основные экраны: Pulse (граф жизни), «Сегодня», Tasks, Projects, Resources. Есть необязательные интеграции Telegram и Obsidian.

Стек: Pub workspace, Flutter, Dart `^3.12.0`, Drift/SQLite, RxDart, SharedPreferences, Mockito и Flutter Test. Версия Flutter в CI — `3.44`; зависимости и ограничения сверяй с `pubspec.yaml` и `.github/workflows/flutter-ci.yml`.

Общайся с пользователем по-русски, если он не попросил иначе. Сначала объясняй результат и практический смысл, затем необходимые технические детали.

## Текущее архитектурное решение

Завершены 15 этапов перехода от структуры в `lib/features` к модульному монолиту. Принцип «everything is a plugin» означает сборку встроенных модулей через контракты и реестры. Динамическая загрузка стороннего кода не реализована.

**Не продолжай миграцию ради самой модульности.** Последняя оценка: отделение API, логики и хранения полезно, но дальнейшее дробление и перенос каждого экрана в пакет могут быть избыточны. Предпочитай конкретные пользовательские функции и исправления. Следующие этапы в историческом документе — возможные направления, а не автоматическое задание новому чату.

Не откатывай существующие границы без конкретной причины. Не переписывай ядро на Rust без измеренного узкого места или отдельной задачи. Не разделяй общую SQLite-базу без необходимости и плана миграции.

Подробности и история: [docs/modular-architecture.md](docs/modular-architecture.md). Старые числа тестов, ошибки и указания «дальше» внутри отдельных этапов относятся к моменту их выполнения; актуальнее текущий код, конец документа и задача пользователя.

## Карта проекта

| Место | Назначение |
| --- | --- |
| `lib/main.dart`, `lib/app.dart` | Запуск приложения и корневой виджет |
| `lib/app/dependency_container.dart` | Сборка зависимостей, запуск/закрытие ресурсов; глобального service locator нет |
| `lib/app/plugins/` | Подключение конкретных хранилищ и UI к плагинам |
| `lib/main_screen.dart` | Оболочка с зарегистрированными экранами и навигацией по ID |
| `lib/features/workspace/` | Пользовательская раскладка областей, контроллер и UI рабочего пространства |
| `lib/features/*/data/` | Реализации Drift и адаптеры хранения |
| `lib/features/*/presentation/` | Оставшиеся экраны, специальные поля и визуальные адаптеры приложения |
| `lib/core/database/database.dart` | Общая база и миграции |
| `lib/core/theme/`, `lib/core/ui/` | Тема приложения и общие контролы |
| `test/architecture/` | Проверки границ, публичных импортов и карта удалённых путей |
| `test/support/test_app.dart` | Тестовая сборка с SQLite в памяти и подставными настройками |

### Пакеты

- `core_contracts`: общие `Wrapped` и `StorageException`.
- `tasks_api`, `projects_api`, `habits_api`, `goals_api`, `spheres_api`, `notes_api`: публичные модели и контракты запросов/команд; без Flutter, SQLite и приложения.
- `tasks_plugin`, `projects_plugin`, `habits_plugin`, `goals_plugin`, `spheres_plugin`: функциональная логика, регистрация вкладов в граф/UI и владение ресурсами. Чистые точки входа — `*_logic.dart`.
- `lifegraph_plugin`: проекция графа, состояние Pulse и открытых графов, сохранение координат/заметок. Чистая точка входа — `lifegraph_logic.dart`.
- `resources_plugin`: состояние библиотеки и операции через контракты заметок.
- `today_plugin`: дата и раскладка экрана «Сегодня». Получает панели через фабрику, не импортирует бизнес-API или реализации функциональных плагинов.
- `plugin_runtime`: `AppPlugin`, `PluginHost`, порядок зависимостей, откат запуска, остановка, `OwnedStreams`, `DebouncedWriter`.
- `plugin_ui`: реестр экранов, панелей, действий и настроек; навигация и отзыв старых контекстов.
- `graph_api`: данные узлов, поставщики, команды, позиции и контракты хранения графа.
- `graph_ui`: регистрации карточек/редакторов/действий, `GraphNodeActionContext`, `GraphModulePlugin`.
- `graph_canvas`: общий канвас и жесты; не знает бизнес-модули.
- `graph_components`: общие карточки и формы через `GraphNodeData`, `GraphNodeDraft`, `GraphNodeComponentSpec`; оформление через `GraphComponentPalette` в теме.
- `telegram_plugin`, `obsidian_plugin`: интеграции через публичные контракты; без зависимости на приложение или Drift.

UI пока извлечён не полностью. Например, `TasksScreen`, `ProjectsScreen`, панели Pulse и специальные поля расписания/статусов остаются адаптерами приложения. Это допустимая граница, а не ошибка, которую нужно немедленно исправить.

## Как вносить изменения

1. Используй существующий модуль. Новые пакеты, интерфейсы и универсальные механизмы добавляй, когда этого требует задача.
2. Передавай зависимости через конструкторы. Не обращайся из функции к общему контейнеру и не импортируй конкретное хранилище вместо доступного контракта.
3. Между пакетами используй публичные точки входа. Ручной код не должен импортировать чужой `src` или зависеть из пакета на `package:life_os/`.
4. Не возвращай удалённые пути и файлы совместимости. Карта замен: [test/architecture/retired_paths.json](test/architecture/retired_paths.json). Например, контейнер импортируется из `app/dependency_container.dart`, модели задач — из `tasks_api`, их логика — из `tasks_plugin/tasks_logic.dart`. Старых `core/di.dart` и `features/tasks/domain/task_model.dart` больше нет.
5. UI-модули подключай через реестры. Не добавляй в оболочку условия для каждого нового экрана или типа узла графа.
6. Сохраняй существующий стиль кода и оформления. Избегай массового форматирования, обновления зависимостей и исправления посторонних предупреждений в обычной задаче.

### Повторное использование UI

Публичные панели: `tasks_plugin/tasks_panels.dart`, `habits_plugin/habits_panels.dart`, `projects_plugin/projects_panels.dart`. Их `*PanelModule` создают собственные модели, фильтры и подписки, используя общие API данных. Пример композиции: `lib/app/plugins/today_plugin_adapter.dart`.

У каждого экземпляра панели должен быть уникальный ID. Дата и фильтры составного экрана не должны изменять состояние основных экранов. Данные синхронизируются через существующие API и потоки.

Вкладка «Пространство» подключается через `workspace_plugin_adapter.dart`.
Она поддерживает задачи, календарь, иерархию, привычки, статистику и сферы.
TasksViewModel и используемая HabitsViewModel принадлежат отдельной области;
панели статистики/сфер читают общую проекцию Pulse без изменения её фильтров.
Карточки задач передаются в TasksPanel через taskBuilder из адаптера приложения
(TaskCard). Привычки используют общий с Pulse TodaysHabitsPanel с кнопками
редактирования и карты дней; кнопка управления привычками убрана из toolbar Pulse.
Доступны разделение/закрытие и изменение размеров, сохранение дерева раскладки в
SharedPreferences (`workspace.layout.v1`). На узком экране области переключаются
по одной. Новые виды содержимого добавляй через список WorkspaceEditor в адаптере,
не через условия в MainScreen; ресурсы экземпляров принадлежат модулю.

Изменение раскладки доступно в режиме «Изменить / Готово». По умолчанию он
выключен: шапки скрыты, рамок областей нет. Разделители видны и позволяют менять
размеры в обоих режимах. Контроллер блокирует изменение содержимого, разделение
и закрытие областей вне edit; в тестах этих команд включай setEditing(true).

Для стандартной карточки и форм нового типа графа используй `GraphNodeComponentSpec`, `graphNodePresentation`, `graphNodeEditor`, `graphChildForm`. Специальные поля передавай через `editFields`/`createFields`, а бизнес-команды определяй в своём модуле. Общий пакет не должен знать `TaskStatus` или перечисление встроенных типов.

### Жизненный цикл

- `PluginHost` запускает зависимости раньше потребителей и останавливает в обратном порядке. Например: `spheres.graph` → `goals.graph` → `projects.graph`.
- Модуль владеет своими подписками, моделями, очередями и таймерами. Остановка запрещает новые операции, завершает принятые записи и освобождает ресурсы, в том числе после частичного запуска.
- Ошибка одной процедуры очистки не должна мешать остальной очистке; вызывающий код должен получить ошибку.
- Сохранённый callback или форма после остановки/перезапуска не должны менять новый экземпляр модуля. Используй существующие проверки активности/поколения и `GraphNodeActionContext`.
- При повторном запуске модели создаются заново. Не дели изменяемые фильтры между независимыми панелями случайно.

## Сохранность данных

- На последней проверке схема SQLite — v9. Сохраняй существующие данные; не удаляй и не пересоздавай пользовательскую базу или vault для проверки изменений.
- Удаление поддерева графа выполняет `DriftGraphDeletion` одной транзакцией, включая невидимых потомков. Сохраняй семантику `keepChildren`.
- Не заменяй обновление задачи на `INSERT OR REPLACE`: это может удалить связанные журналы времени. Не теряй теги, UUID и посторонние поля при записи устаревшей карточки.
- Сохраняй формат хранения статусов и исторических JSON. Отложенные записи должны захватывать исходные ID/контекст, поддерживать flush и завершаться до закрытия хранилища.
- В тестах используй память, временные каталоги и `createTestApp`. Не запускай интеграции на реальных настройках пользователя ради проверки рефакторинга.

Telegram/Obsidian можно отключить через `--dart-define=ENABLE_TELEGRAM=false` и `--dart-define=ENABLE_OBSIDIAN=false`; в тестовой сборке доступны соответствующие параметры контейнера. Регистрация Telegram сама по себе не должна запускать polling.

## Проверка изменений

Запускай команды из корня workspace. В текущей Windows-среде Flutter установлен в `C:\flutter`; если команды отсутствуют в PATH, доступны `C:\flutter\bin\flutter.bat` и `C:\flutter\bin\cache\dart-sdk\bin\dart.exe`. На другой машине проверь её окружение.

```sh
# При изменении зависимостей
flutter pub get

# При изменении Drift, аннотаций Mockito или затронутых генерацией типов
dart run build_runner build

# Быстрая проверка границ и инфраструктуры; добавь тесты изменённой функции
flutter test test/architecture test/core/plugins test/core/storage test/app

flutter analyze --no-pub
flutter test --no-pub
```

После удаления файла workspace-пакета build_runner иногда хранит старую ссылку в asset graph. При такой ошибке выполни `dart run build_runner clean`, затем повтори генерацию. Не редактируй `.g.dart`/`.mocks.dart` вручную. Устаревший флаг `--delete-conflicting-outputs` текущий генератор игнорирует.

Чистую логику можно проверять без Flutter, например:

```sh
dart test test/features/tasks/domain/tasks_plugin_logic_test.dart test/features/projects/domain/project_contracts_test.dart
```

Для изменений только документации не нужен полный прогон приложения. Для кода сначала проверь затронутое поведение, затем выполни соответствующие архитектурные и общие проверки. Не ослабляй тесты или правила анализа, чтобы скрыть регрессию.
