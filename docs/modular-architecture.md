# Переход к модульной архитектуре

Внедрён первый рабочий этап: контракты задач, хост плагинов и независимый пакет Telegram.
Приложение пока содержит остальные функции в lib/features; это промежуточное состояние миграции.

## Текущие границы

- packages/tasks_api: модели Task, Tag, WorkLog, стабильный порядок TaskStatus и контракты TaskQueries, TaskCommands, TasksApi, WorkLogsApi. Пакет не зависит от Flutter, Drift или приложения.
- packages/plugin_runtime: AppPlugin и PluginHost. Проверка зависимостей, порядок запуска, обратный порядок остановки, откат частичного запуска, последовательное выполнение start/stop.
- packages/telegram_plugin: Telegram-команды, parser, polling и форматирование. Зависит от tasks_api и plugin_runtime; не импортирует life_os или Drift.
- lib/features/tasks/data/telegram_task_queries.dart: SQL-адаптер контракта TelegramTaskQueries. Возвращает доменные DTO; соединение с SQLite не пересекает границу плагина.
- lib/app/dependency_container.dart: точка сборки приложения. Создаёт реализации, передаёт зависимости, запускает и завершает ресурсы. Экземпляры независимы; глобального контейнера нет.
- lib/core/di.dart и прежние пути моделей/Telegram оставлены как совместимые exports на время переноса потребителей.

Плагины включаются в сборку. Регистрация плагина не запускает polling: бот включается пользователем.
Отключение Telegram при сборке:

~~~sh
flutter run --dart-define=ENABLE_TELEGRAM=false
~~~

При таком запуске сервис не создаётся, плагин не регистрируется, кнопки бота не отображаются.
Для тестов и альтернативного состава приложения доступен DependencyContainer(enableTelegram: false).
Это отключение функции внутри общей сборки; полностью отдельный pubspec без зависимости telegram_plugin пока не выделен.

## Правила для следующих модулей

1. API содержит модели и команды/запросы, необходимые потребителям. Flutter-цвета и иконки живут в presentation.
2. Зависимости передаются через конструкторы. Модуль не получает глобальный service locator.
3. Плагин владеет подписками, таймерами и сетевыми процессами. stop() должен освобождать и частично созданные ресурсы.
4. Повторные start/stop безопасны. Ошибка остановки не препятствует попытке освободить остальные ресурсы; хост возвращает сведения об ошибках.
5. Операции, требующие атомарности, выполняются через прикладной контракт и одну транзакцию. События не заменяют транзакции.
6. Приватные реализации другого пакета не импортируются. Проверки в test/architecture запускаются обычным flutter test.
7. Критичные записи поддерживают flush() и завершаются до закрытия экрана/модуля.

## Исправления сохранности данных

- getById загружает задачу вместе с тегами в одной транзакции.
- INSERT OR REPLACE заменён UPSERT: обновление задачи не вызывает каскадного удаления рабочих логов.
- Включены SQLite foreign_keys. Существующие записи и файл базы не удаляются и не пересоздаются.
- DriftGraphDeletion удаляет произвольное поддерево по данным базы, включая невидимые в UI элементы, внутри одной транзакции. keepChildren отсоединяет сохранённые дочерние записи.
- Отложенные записи заметок и координат сохраняют снимок с ID исходной сферы. flush выполняется перед переключением и выходом; неудачную запись можно повторить.
- ResourcesViewModel подписывается на источники один раз, публикует начальные данные, сохраняет ошибку сканирования и освобождает подписки.
- WorkLogsSection получает WorkLogsApi явно, без доступа к контейнеру.

Включение foreign_keys предотвращает новые нарушения для объявленных FK, но не исправляет исторические осиротевшие строки. Автоматическая очистка пользовательских данных не выполняется. Перед будущей миграцией FK между проектами, целями и сферами нужен отдельный анализ PRAGMA foreign_key_check и стратегия сохранения обнаруженных записей.

## Следующие этапы

1. Выделить notes_api и obsidian_plugin. Модель заметки должна быть независимой от GraphView, а построение HierarchyNode — выполняться в presentation.
2. Добавить plugin_ui с регистрацией экранов, действий, настроек и панелей, затем убрать специфичные для Telegram зависимости из оболочки.
3. Выделить API сфер/целей и заменить GraphBuilder набором GraphContributor. Типы/рендереры узлов регистрируются модулем.
4. Перенести Tasks, Projects, Habits и LifeGraph в пакеты по устойчивым границам. Не создавать отдельный пакет ради каждого класса.
5. Оставить общую SQLite-базу и централизованный план миграций до появления проверенной необходимости разделять хранилища.
6. Восстановить оставшиеся старые тесты календаря/таймлайна и UI; фиксировать отдельные поведенческие изменения отдельно от переноса пакетов.

Rust не требуется для этих границ. При появлении измеренного узкого места или второго клиента можно заменить реализацию конкретного API нативным адаптером, сохранив потребителей. Загружаемые сторонние плагины и sandbox в этот этап не входят.
