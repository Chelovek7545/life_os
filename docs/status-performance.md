# SQLite в фоне и команды статуса — 17.11.2026

## Адресное журналирование — 19.11.2026

Схема SQLite v13 добавляет локальный индекс `sync_entity_heads`. Он хранит
однозначные текущие версии и признаки блокировки по ключу сущности. Пустой
ключ — маркер актуальности; триггеры журнала сбрасывают его при изменении
`sync_revisions`. Индекс восстанавливается из журнала после миграции при
первом обращении. Входящие ревизии и сложные операции сохраняют полную проверку
и обновляют индекс после неё. Формат ревизий и обмен между устройствами прежние.

Обычная смена статуса проверяет только затронутую запись и её текущую версию.
Статус, новая ревизия и индекс фиксируются одной транзакцией. Статус сущности с
конфликтом или ожидающей ревизией менять нельзя. При ожидающих ревизиях других
сущностей запись проходит прежнюю полную проверку. Чтение списков получает
токены версий по ключам из индекса и по-прежнему сравнивает payload снимка.
Чекбоксы продолжают отображать состояние из потока базы.

Одинаковый замер до/после: Windows, временная файловая SQLite в фоне, учёт
синхронизации включён. Медиана шести изменений после прогрева, в миллисекундах.

| Задач + ворклогов | Задача: до → после | Ворклог: до → после | После, ещё 1000 ревизий: задача / ворклог |
| --- | --- | --- | --- |
| 200 + 200 | 139,68 → 11,59 | 145,07 → 11,09 | 12,27 / 11,61 |
| 1000 + 1000 | 878,64 → 10,96 | 663,59 → 10,63 | 10,86 / 9,97 |

Измерялось время выполнения команды до коммита, без активных подписок и
отрисовки. Замер не покрывает первый пересчёт индекса после миграции и запасной
путь с ожидающими ревизиями.

```powershell

$env:STATUS_BENCH_EXTRA_REVISIONS = '1000'

Remove-Item Env:STATUS_BENCH_EXTRA_REVISIONS
```

## Исходное изменение — 17.11.2026

Нативная база открывается через `NativeDatabase.createInBackground`. SQLite
исполняет SQL на отдельном isolate; `AppDatabase.close` закрывает worker.
Путь пользовательской базы и схема v12 не менялись.

`TaskCommands.setTaskStatus` и `WorkLogsApi.setWorkLogStatus` обновляют только
статус (для задачи также updatedAt). Чекбоксы, канбан, массовое завершение и MCP
completeTask используют узкую запись. Полные редакторы сохраняют CAS по
storageRevision. Команды статуса применяются к текущей записи по ID, сохраняют
блокировку конфликтов/pending и транзакционную запись журнала. Оптимистический
UI и оптимизация SyncGraph в это изменение не входят.

## Воспроизводимый замер

Из корня workspace:

```sh
flutter test --no-pub tool/performance/status_write_benchmark_test.dart --concurrency=1 --reporter expanded
```

Windows, тестовый JIT-режим, временные файловые SQLite. Каждый размер означает
равное количество задач и ворклогов. Сравниваются четыре сочетания старой/узкой
записи и SQLite в основном/фоновом isolate, с bootstrap синхронизации и без.
Числа ниже — медианы шести последовательных переключений после одного прогрева.
Старый путь задачи включает getById и полный updateTask, как прежний чекбокс.
Старый путь ворклога использует заранее загруженный снимок, как UI.
Активных экранных подписок и отрисовки в замере нет.

| Задач + ворклогов | Учёт синхронизации | Задача: раньше → теперь, мс | Ворклог: раньше → теперь, мс |
| --- | --- | --- | --- |
| 200 + 200 | Нет | 9,02 → 7,98 | 8,19 → 7,89 |
| 1000 + 1000 | Нет | 8,11 → 7,96 | 8,13 → 8,04 |
| 200 + 200 | Да | 170,84 → 132,50 | 129,60 → 130,03 |
| 1000 + 1000 | Да | 789,74 → 590,10 | 581,79 → 592,60 |

«Раньше» — полное обновление, SQL в основном isolate. «Теперь» — узкая команда,
SQL в фоне. Для отделения факторов: при 1000 + 1000 и учёте синхронизации узкая
команда задачи без фонового SQLite занимала 603,10 мс; полная запись с фоновым
SQLite — 923,43 мс. Перенос SQL сам по себе не гарантирует уменьшения времени
коммита: появляется обмен сообщениями между isolate. Узкая команда убирает
лишнее чтение доменного снимка/ревизии и пересохранение тегов.

Отдельная искусственная SQL-проба вычисляет сумму рекурсивной последовательности
из 2 млн чисел и измеряет максимальный разрыв между callback таймера основного
isolate. Результат: 243,44 мс с обычным NativeDatabase и 2,52 мс с фоновым.
Это проверка отзывчивости event loop при SQL-нагрузке, а не время кадра приложения.

Запись задачи ускорилась примерно на 22–25%; ворклог не получил заметного
ускорения. Полные снимки и пересборка SyncGraph остаются на вызывающем isolate и
по-прежнему определяют большую часть задержки подключённой к синхронизации базы.
Один прогон не задаёт гарантированные задержки; на Windows/Android Release ещё
нужен полевой замер с пользовательскими сценариями и профилем кадров.
