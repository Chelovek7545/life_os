подтверждением, отзыв доступа и настройки/конфликты. Проверено через настоящие

## Включение

Модуль `sync.local` включается сборочным параметром; в исходном коде он
по умолчанию выключен. Регистрация идёт через plugin_ui, без условий MainScreen.

```sh
flutter run --dart-define=ENABLE_SYNC=true
flutter build windows --release --dart-define=ENABLE_SYNC=true
```

Готовая Windows-сборка: `build/windows/x64/runner/Release/Pulse.exe`.
Рядом с Pulse.exe должны оставаться её DLL и каталог data.

Включение модуля регистрирует секцию «Локальная синхронизация» в настройках
и подготавливает защищённые ключи. Сетевой listener и учёт БД запускаются
только явными действиями пользователя. Web не регистрирует модуль;
sync_native.dart использует заглушку без dart:io.

## Подключение двух устройств

Кнопка синхронизации находится справа в верхней панели экрана Pulse. Панель
показывает подключённые устройства, ход обмена, время последнего обмена и
изменения, требующие внимания. Нажмите «Синхронизировать» рядом с устройством
или «Настройки», чтобы перейти к сопряжению, приёму и разрешению конфликтов.
Если связь прервалась, проверьте, включён ли приём на втором устройстве, и
повторите обмен. Тест TLS проверяет передачу сохранённой офлайн-задачи после
возвращения второго устройства и отсутствие дубликатов при повторном обмене.

1. Откройте приложения в одной локальной сети. На экране Pulse нажмите кнопку
   синхронизации справа вверху и выберите «Настройки».
   Проверьте, что открыта сборка с ENABLE_SYNC=true: старая запущенная версия
   может иметь такое же имя окна Pulse, но не содержать этого раздела.
   Поле IP относится к текущему устройству: выбирается адрес
   Wi-Fi/Ethernet, его можно исправить вручную. Обнаружения mDNS пока нет.
2. На устройстве с исходными данными нажмите «Создать пространство на этом
   устройстве». Bootstrap сохраняет прежние ID и даты, создаёт журнал и UUID
   тегов одной транзакцией. При нарушенных связях он откатывается.
3. Нажмите «Пригласить устройство», скопируйте приглашение и передайте его
   второму своему устройству. Оно одноразовое, действительно пять минут.
4. На втором устройстве вставьте приглашение и нажмите «Присоединиться с
   пустой базой». Синхронизируемые сущности должны отсутствовать; независимые
   заполненные базы автоматически не объединяются. Проверка повторяется
   после подтверждения, поэтому новые локальные записи за время ожидания
   также не будут перезаписаны.
5. На исходном устройстве подтвердите появившийся запрос. Срок подтверждения —
   две минуты. Отклонение, истечение срока или остановка аннулируют запрос.
6. Нажмите «Синхронизировать» у подключённого устройства. Обмен выполняется
   в обе стороны. Оба приложения должны быть открыты и доступны по LAN.

Порт по умолчанию — 48766. Передача идёт только по HTTPS на локальные
IP-адреса; HTTP, публичные IP и произвольные DNS-имена отклоняются. Параметры
сервера и хранилище ключей инъецируются для тестов; порты тестов случайные,
адреса — loopback. Сетевого polling и фонового сервиса пока нет.

Переключатель «Приём по локальной сети» закрывает входящий listener. Явный
исходящий обмен с доступным подключённым устройством остаётся возможным.
После перезапуска приём нужно включить снова; ключи и список устройств
сохраняются. Изменения БД продолжают журналироваться без открытого listener.

## Повторное подключение и отзыв

«Отозвать доступ» удаляет ключ пары на текущем устройстве. Следующие запросы
партнёра отклоняются; ранее принятая транзакция завершается. Полученные данные
не удаляются удалённо.

После смены адреса или отзыва можно создать новое приглашение и использовать
«Подключить приглашение в этом пространстве» на втором устройстве. Повторное
сопряжение требует подтверждения; для уже известного peer сначала отзывается
прежний доступ на принимающем устройстве. Существующая база допускается только
в том же datasetId, с сохранением deviceId и всех данных. Присоединиться таким
способом к другому пространству нельзя.

## Конфликты и ожидающие записи

Счётчики не называют данные полностью синхронизированными при наличии
конфликтов или pending. «Разрешить конфликты» показывает сохранённые варианты,
источник, поля и доступные названия связанных сущностей. Выбор версии создаёт
новую ревизию с проверкой показанного набора вершин. Если версии уже изменились,
нужно перечитать список.

При delete против edit сохраняются оба варианта, а в бизнес-таблицах действует
удаление. Можно подтвердить удаление; восстановление под старым ID запрещено.
Создание отдельной восстановленной копии этим экраном пока не реализовано.

«Просмотреть ожидающие изменения» позволяет явно:

- переименовать конфликтующий тег;
- снять выбранную связь задачи/проекта/цели или теги задачи;
- перенести сохранённый WorkLog в существующую живую задачу.

Все исправления сохраняют историю и проверяют исходную основу. Неполные группы,
неизвестные причинные родители и ещё не полученные данные нельзя обойти
исправлением формы: сначала требуется повторный обмен. Программа не обнуляет
ссылки и не объединяет одноимённые теги автоматически.

## Ключи и протокол

Используется TLS 1.2+ сервера с закреплённым SHA-256 отпечатком сертификата.
Для каждой пары генерируется отдельный случайный 256-битный bearer-ключ;
это аутентификация пары поверх TLS, не mutual TLS с клиентскими сертификатами.
Сертификат создаёт [basic_utils](https://pub.dev/packages/basic_utils), TLS
выполняет dart:io. Собственных шифров и протоколов подписи нет.

Закрытый ключ и ключи пар хранятся одной версионированной записью через
[flutter_secure_storage](https://pub.dev/packages/flutter_secure_storage).
SQLite и SharedPreferences не содержат эти секреты. На Android resetOnError
выключен: сбой защищённого хранилища оставляет модуль офлайн, без автоматического
сброса ключей или plaintext fallback. Основное приложение продолжает работать,
повторное действие может заново открыть хранилище.

Приглашение содержит адрес, отпечаток, dataset/device ID, случайный одноразовый
секрет и срок. Секрет передаётся только после проверки закреплённого сертификата;
клиент использует SecurityContext без системных корней и запрещает redirects.
Host подтверждает отдельный nonce запроса, поэтому старое подтверждение не
может одобрить новый запрос того же устройства после restart.

Эндпоинты `/v1/pair`, `/v1/hello`, `/v1/cursor`, `/v1/pull`, `/v1/push` принимают
ограниченные JSON-сообщения. Push связывает источник batch с авторизованным peer;
dataset и версия протокола проверяются до доступа к данным. Ack следует за
коммитом существующего SyncStore. Повторы и неполные группы сохраняют прежнюю
идемпотентность. Ретрансляция допустима только внутри доверенной личной группы;
revision.deviceId — метаданные автора, не криптографическая подпись.

По умолчанию: до восьми принятых операций, до 6 MiB на HTTP-сообщение,
15 секунд на обычный запрос, до 100 ревизий в пачке с прежним лимитом 4 MiB.
Остановка отзывает поколение, закрывает клиентские соединения/listener,
завершает подготовку ключей и уже принятые операции БД до закрытия AppDatabase.
Сбой одной очистки не отменяет остальные; ошибки возвращаются владельцу.

## Проверки и оставшаяся работа

### Полевой сценарий Windows ↔ Android

На обоих устройствах нужна сборка с ENABLE_SYNC=true. Android APK собирается
командой `flutter build apk --release --dart-define=ENABLE_SYNC=true` и находится
в `build/app/outputs/flutter-apk/app-release.apk`. Установка обновлением сохраняет
данные; удалять приложение или очищать его хранилище для теста не нужно.
Если база телефона уже заполнена независимо, первый тест присоединения
останавливается: объединения двух независимых пространств пока нет.

После сопряжения выполните по порядку:

1. Создайте на Windows задачу «SYNC-PC», запустите обмен и проверьте её появление
   на телефоне. Измените название на телефоне и запустите обмен обратно.
2. Завершите задачу на телефоне. После обмена статус на Windows должен совпасть.
3. Отключите сеть телефона, создайте «SYNC-OFFLINE» и измените существующую
   задачу. После возврата сети и ручного обмена изменения должны появиться
   на Windows без дубликатов.
4. До очередного обмена задайте одной задаче разные названия на двух устройствах.
   После обмена должен появиться конфликт. Выберите вариант в настройках,
   повторите обмен и проверьте одинаковое название и отсутствие конфликта.
5. Удалите тестовую задачу, повторите обмен дважды. На другом устройстве она
   должна исчезнуть и не восстановиться после второго обмена.
6. Перезапустите оба приложения. Устройства должны остаться в списке; включите
   приём на принимающей стороне и проверьте обмен новой тестовой задачей.

Выбирайте IP Wi-Fi, а не VPN/WSL/виртуального адаптера. При тайм-ауте проверьте
доступность обоих устройств в одной сети и разрешение входящего TCP 48766
в брандмауэре Windows для частной сети. Результат каждого шага фиксируйте
отдельно; успешная сборка APK или loopback-тест не подтверждает полевой обмен.

Проверки используют память/временные базы и подставное хранилище секретов;
пользовательский vault и системное хранилище ключей для тестов не открываются.
Проверены реальные TLS, ручное подтверждение, несовпадающий pin, отказ/повтор
приглашения, заполненная база и запись во время pairing, отзыв, restart,
остановка во время приёма и подготовки ключей, конфликты и исправление pending.
Панель проверяется widget-тестами, включая узкий экран и старые callbacks.

Далее нужны завершение полевого прогона двух устройств, привычки, файлы/Canvas,
обнаружение устройств и оптимизация проекций/истории. Снимки/компактация журнала,
многопользовательские права и недоверенные ретрансляторы не реализованы.

Подробная архитектура: [device-sync.md](device-sync.md).
